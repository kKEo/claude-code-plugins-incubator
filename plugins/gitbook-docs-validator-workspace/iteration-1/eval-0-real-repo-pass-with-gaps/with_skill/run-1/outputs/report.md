**Verdict:** PASS with deviations — the landing page and all three books are present, published and
structurally sound (0 errors from `validate_docs.py`); what remains is repository integration that
still says "two guides", a few README/lead-paragraph conventions, and version text that will drift.
Books found: user=`user/`, operator=`operator/`, tester=`tester/`

Checked on branch `feature/living-system-scenarios` (commit `b97e59e`), 2026-10-19, with
`python3 scripts/validate_docs.py docs/guide --repo-root .` (exit 0: 0 errors, 2 warnings, 3 notes)
followed by a manual read of `index.html`, the three book READMEs, the three `SUMMARY.md` files,
`user/quick-start.md`, `operator/config/environment.md`, `tester/start/running.md`,
`tester/gates/ci.md`, `tester/contributing/README.md`, the generated scenario pages, and the
repository files the template names (root `README.md`, `docs/README.md`, `Makefile`,
`.github/workflows/docs.yml`, `scripts/docs-check.sh`).

## Structural failures (must fix)

None. Every check the script treats as an error passes:

- `index.html` has `<title>`, `<meta name="description">`, a lede, one card per book with audience
  tag, title, summary, three bullets and `href="<book>/"`, a footer with repository and licence,
  and light/dark colours with no JavaScript.
- Each book has `README.md`, `SUMMARY.md`, `.gitbook.yaml` (`root: ./`, readme/summary structure)
  and `book.toml` (`src = "."`, `build-dir = "../../../site/<book>"`, `site-url = "/memors/<book>/"`,
  `create-missing = false`).
- Every SUMMARY starts with `README.md`; every page on disk is listed (no orphans); every listed
  file exists; parts are numbered `Part I..VII` (operator) and `Part I..V` (tester) with a
  `README.md` per part directory; nesting stays within three levels.
- One H1 per page on line one, no skipped heading levels, every image exists with sentence-length
  alt text, no unused images, every relative link and anchor resolves inside the docs root.
- Required pages per role are all present: user (quick start, FAQ/troubleshooting, glossary, plus
  everyday use, trust, privacy, use cases); operator (how it works, install, configuration,
  commands, monitoring, operations, glossary); tester (running the tests, what is tested where,
  CI gates, adding tests with PR checklist, exploratory, appendix).
- Generated pages (`tester/scenarios/catalogue.md`, `gaps.md`, `log/README.md` and the three
  `log/*.md`) carry the `<!-- Generated by ... Do not edit ... -->` marker right after the H1, and
  the freshness test passes (`go test ./internal/eval/scenario/book/` → ok), so they have not been
  hand-edited.

## Template deviations (judge)

Repository integration (template §8) still reflects the two-book era:

- `README.md:174-175` (repo root) — the template wants the root README to link **every** book. It
  links the user and operator guides only, and says "Both guides are published to GitHub Pages",
  while the tester guide (`docs/guide/tester/`) exists and is built by `make docs`. A reader of the
  root README cannot find the tester book. Not reasonable to keep; a one-line fix.
- `docs/README.md` — lists all three books (good) but does not mention the landing page
  `docs/guide/index.html`, which the template's docs index should name as the site's front door.
  Minor.
- `scripts/docs-check.sh:2` — the header comment says "keep the user and operator guides honest";
  the link check in fact walks all of `docs/guide/` (line 50), so the tester book is covered, but
  the comment is stale. Cosmetic.
- `docs/guide/operator/README.md:1` vs `operator/SUMMARY.md:3` — the H1 is "memors-mcp operator
  guide" while SUMMARY calls the page "Introduction" (script note). The sidebar and the page title
  disagree; the user and tester books match theirs ("Welcome", "For testers"). Harmless, but easy
  to align.

Book READMEs (template §5):

- `docs/guide/tester/README.md` — the template asks for a reading-map table (`| Part | Read it
  when you need to… |`, every row a link). The tester README routes the reader with a bulleted
  "Where to start" list plus a "gates at a glance" table whose rows link to pages. The routing
  works and the script accepted the table, but it is not the `Part → when` shape the operator
  book uses, so a reader who jumps between the two advanced books sees two different maps.
  Reasonable as-is; a `| Part | Read it when… |` table would make the two books rhyme.
- `docs/guide/operator/README.md:31` — "Defaults quoted here are the shipped values for v1.4"
  (script note). `CHANGELOG.md` has an `[Unreleased]` section above `[1.4.0]`, and
  `operator/monitoring/catalogue.md:3` already says "v1.4 plus the unreleased section", so the
  two statements about which version the book describes are not the same. Also
  `operator/config/profiles-json.md:7,62` pins behaviour to "in v1.4". These will drift at the
  next tag. Reasonable to keep if the release checklist (`operations/release.md`) bumps them;
  otherwise reword to "the current master" or point to `memors-mcp version`.

Pages (template §6):

- Lead paragraph missing on 19 pages — the first body line after the H1 is already an `##`
  heading, so the page never says what it is for. In the tester book, where the template expects
  the hardest-working leads, this includes the two "must have" pages `tester/start/running.md`
  (`## What you need`) and `tester/contributing/README.md` (`## Which kind of test?`), plus
  `tester/start/map.md`, `tester/gates/fuzz-race.md`, `tester/explore/retrieval.md`,
  `tester/appendix.md`. In the user book: `faq.md`, `privacy.md`, `why.md`, `use-cases.md`,
  `everyday/asking.md`, `everyday/saving.md`. In the operator book: `install/upgrading.md`,
  `install/layout.md`, `intro/overview.md`, `lifecycle/ingest.md`, `operations/integrity.md`,
  `operations/export.md`, `monitoring/metrics-endpoint.md`. For reference pages (FAQ, glossary,
  environment table) a missing lead is defensible; for `running.md` and `contributing/README.md`
  one sentence ("Run everything once, then narrow; this page covers the make targets and what to
  do when something fails") is worth adding.
- `docs/guide/tester/contributing/README.md` — Part V is a single-page part (the directory holds
  only `README.md`, and SUMMARY lists no chapters under it). The template allows it; it just means
  the part README has to be the chapter rather than a table of contents, which it is.

Tone and fit (template §6 tone row), checked by reading:

- User book: plain language holds. "MCP" appears six times, all in `menu-bar.md` or the glossary,
  and "namespace" only as a gloss for "shelf"; `quick-start.md` states "This takes about ten
  minutes". Good.
- Operator book: `config/environment.md` quotes a default and a file path for every variable;
  `profiles show` and `model ls`, which it names, exist in `internal/cli/kbcmds.go`. Good.
- Tester book: `start/running.md`, `gates/ci.md` and `contributing/README.md` name make targets,
  workflow files, packages and test names on every screen. Good.
- Template fit: the three-reader split fits this project well (a single binary with a real
  operator and a heavy test harness); no reason to deviate from the template's shape.

## Suggestions

- Add the tester book to the root `README.md` docs section and change "Both guides" to "The
  three guides" (or list them), and add `docs/guide/index.html` to `docs/README.md`.
- Give `tester/README.md` a `| Part | Read it when you need to… |` table (five rows, one per part,
  plus the appendix) above or instead of the "Where to start" bullets, so the two advanced books
  open the same way.
- Decide one phrase for the version the operator book describes and use it in `README.md`,
  `monitoring/catalogue.md` and `config/profiles-json.md`; add "update version text in the
  operator guide" to `operations/release.md` if it is not already there.
- Add one-sentence leads to the pages listed above, starting with the two tester pages.
- Align the operator README's SUMMARY title with its H1 (either "Introduction" as the H1 or
  "memors-mcp operator guide" in SUMMARY).
- Refresh the header comment of `scripts/docs-check.sh` to say it covers all three guides, and
  consider a fourth check: every `make` target named in `tester/start/running.md` exists in the
  `Makefile` (the same drift risk the env-var check already guards against for the operator book).
- The `Updated` dates in `docs/README.md` show 2026-10-03 for the user and operator guides while
  the operator guide now documents the `MEMORS_*` rename of 2026-10-10 (`config/environment.md`
  "Renamed" section); bump the dates when the guides change.
