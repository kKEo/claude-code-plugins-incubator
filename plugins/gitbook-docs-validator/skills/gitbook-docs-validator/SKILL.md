# GitBook docs validator

You are checking a documentation tree against a template that a team already uses and trusts.
The template is one landing page plus exactly three books, each for a different reader:

| Role | Reader | Promise |
|---|---|---|
| **user** | someone new, non-technical | plain words, a timed quick start, everyday tasks, FAQ, glossary |
| **operator** | runs or develops the system | how it works inside, install/deploy, complete configuration reference, monitoring, day-two operations |
| **tester** | checks that changes are safe | how to run the tests, what blocks a merge, how to add tests, how to explore by hand |

The full template, with the reason behind each rule, is in `references/template.md`. Read it
once per session before judging anything the script cannot measure; it is short.

## Workflow

1. **Find the docs root.** It is the directory that holds `index.html` and the book folders
   (each book has `SUMMARY.md`). Usually `docs/guide/`; if the user names a path, use it. If
   several candidates exist, run the script on each or ask which one the user means.

2. **Run the deterministic checks first.**

   ```bash
   python3 <skill-dir>/scripts/validate_docs.py <docs-root> --repo-root <repo-root>
   ```

   Add `--json` when you want to post-process the findings. Exit status 1 means at least one
   ERROR. The script maps folders to roles through aliases (`user`/`getting-started`/…,
   `operator`/`internals`/`deploy`/…, `tester`/`qa`/`testing`/…); if a project uses other names,
   either rename or drop a `.docs-template.json` into the docs root with extra `aliases` (same
   shape as `assets/template.json`). Never "fix" a mismatch by editing the skill's own template.

   What the script covers: landing page cards and links; the three roles present exactly once;
   `README.md`/`SUMMARY.md`/`.gitbook.yaml`/`book.toml` per book; SUMMARY starts with README,
   every page listed (orphans are unpublished pages), every listed file exists, `Part I..N`
   numbering, part directories have a README; one H1 per page on line one (code-fence comments
   are ignored), no skipped heading levels, images exist and carry real alt text, unused images,
   relative links resolve and stay inside the docs root, anchors exist; book README states its
   audience, has a reading-map table and points to the sibling books; each role's required
   pages are present; and, with `--repo-root`, the root README, docs index, Makefile targets,
   docs workflow and docs-check script.

3. **Do the pass the script cannot.** Open the three book READMEs, the landing page and two or
   three pages per book (quick start, one reference page, one tester page) and judge:
   - Does each book speak to its reader? The user book should have no undefined jargon; the
     operator book should quote defaults and name files; the tester book should name commands
     and test files on every page.
   - Does each page's lead paragraph say what the page is for? Does the quick start say how long
     it takes?
   - Does the reading-map table on each README actually route the reader (one row per common
     need, every row a link), or is it a copy of SUMMARY?
   - Are generated pages (HTML comment "Generated by …" after the H1) untouched by hand edits?
   - Does anything reference the code in a way that could drift (version numbers in prose, a
     command the binary no longer has)? Spot-check one or two against the code if the repo is
     present.
   - Is the template itself the right fit here? If a project has a good reason to deviate (for
     example, a product with no operator at all), say so rather than demanding compliance.

4. **Write the report** in this shape, every time, so reports from different projects compare:

   ```markdown
   # Documentation template check: <project>

   **Verdict:** PASS | PASS with deviations | FAIL — one sentence on why.
   Books found: user=<dir>/, operator=<dir>/, tester=<dir>/   (or which is missing)

   ## Structural failures (must fix)
   - <file:line> — what is wrong, and the consequence (e.g. "page is never published").

   ## Template deviations (judge)
   - <file> — the rule, how this project differs, whether the deviation is reasonable.

   ## Suggestions
   - Improvements beyond the template that this project would benefit from.

   ## Not checked
   - What this run could not verify (no repo root, no code to compare against, …).
   ```

   Lead with the verdict and the errors. Group repeated findings ("12 pages have an image
   without alt text, e.g. …") instead of listing each. Quote the script's `file:line` so the
   reader can click through. Keep suggestions separate from failures: a team should be able to
   fix the first list mechanically and discuss the second.

5. **Offer, do not apply.** Unless the user asked for fixes, stop at the report. If they ask,
   fix structural failures first (they are mechanical), re-run the script, and leave template
   deviations as a conversation.

## When the project is not yet using the template

If the tree has one book, or none, the script will report missing roles. Do not pad the report
with every per-page rule; the useful answer is the shape: which roles exist, which are missing,
what the landing page should link, and which existing pages would move into which book.
`references/template.md` §1 and §7 give the target shape and the minimum pages per role.

## Files

- `scripts/validate_docs.py`: the deterministic checks (python3, stdlib only, `--json`).
- `references/template.md`: the template with the reasoning; read before the qualitative pass.
- `assets/template.json`: roles, folder aliases, required pages; override per project with
  `<docs-root>/.docs-template.json`.
